No new decisions were needed — R11 is a mechanical tightening of the T1 rule, covered by Damien Hall's standing instruction. Applied below.

1. **Replication claims bound to the fsync frontier (R11).** A configured follower **MUST** construct every `/sync` `from` value **exclusively** from its verified, fsync-confirmed durable frontier. Receipt, parsing, successful verification, buffered writes, and pending adoption do **not** advance that frontier. After restart, the follower MUST recover and verify its durable frontier **before** issuing any replication claim. The sequencer MUST NOT count a follower claim beyond its own durable frontier. Rationale: the release gate exists to guarantee a released entry survives sequencer loss — a claim built on receipt rather than persistence voids that guarantee. This does not alter the accepted P6 network-position limitation. New regression test: pause a follower immediately before its fsync, trigger another pull attempt, and assert replicated height cannot advance past the follower's previously durable entry.
2. **ChatGPT's five-requirement disposition, recorded.** OWN-01: ready at specification level. AUTH-01: ready at specification level. ATOM-01: ready at specification level. ## Revision 11 — 2026-10-19 (post final attack round): what changed and why

Claude's final attack round (received 2026-10-19 ~10:39 CDT via Damien Hall) found one real finding — **T1**: "replicated height," as specified, can be advanced by anyone sending a GET request, which quietly undoes S1 — plus wording and test gaps (T2–T6). With T1–T3 applied, Claude declares **no further findings at the spec level** on the Phase 1 packet; remaining risk is the recorded known limits (P6 network position, Q2 disk-fill/budget outage) and the Phase 2 items (peer signatures, fork rules, re-issue mechanism). No new decisions were needed — every item is a mechanical application of standing rules; Damien Hall approved on Luna's recommendation ("I trust your recommendations"). Applied below.

1. **Replicated height from configured followers only (T1).** The sequencer's config lists its followers, and **only** pulls from those addresses count toward replicated height. A follower's request `from = h` is its **claim** that it durably holds everything up to h−1 — a claim about its own durable height, not about a response it received. Any `from` greater than durable height + 1 is ignored. **Replicated height = max over configured followers of (from − 1)**, **recomputed from current claims** — never kept as a historical high-water mark (a follower that falls behind must drag the height down with it). Followers must run on **separate hardware** from the sequencer — a same-disk "follower" witnesses nothing. Residual risk: spoofing a configured follower's address takes network position — the same class as the recorded P6 limit, already accepted. New tests: an unlisted source sends `from=tip` → replicated height doesn't move; a listed follower that crashes before its fsync sends a lower `from` on its next pull → replicated height drops accordingly.
2. **Startup drain uses the replicated gate (T2).** **One gate for every release path:** the outbox releases only entries with `height ≤ replicated height` — the S3 startup scan is explicitly subject to this gate (a builder would otherwise release the whole backlog at boot). After any restart, replicated height starts at **0** and rebuilds from follower pulls — releases pause until a follower checks in. The bad sequence this closes: sequencer crash-restarts, the boot drain releases durable-but-unreplicated redeems, the disk then dies → the double release S1 closed. The cautious direction is the default after every boot.
3. **Height glossary (T3).** Three names, two things: on any node, **durable height** = the fsync frontier = the **acknowledged frontier** ("acknowledged frontier" is retired as a separate name and kept only as a defined alias where earlier revisions used it). **Replicated height** is a separate value tracked **only by the sequencer**. Ordering invariant on the sequencer: **replicated ≤ durable**, where durable is the fsync frontier and live state matches durable because live state is only updated after fsync. Which height governs each surface: `/sync` serves up to **durable**; `/status` reports **durable** and (on the sequencer) **replicated**; the outbox releases at or below **replicated**; commits and 200 responses happen at **durable**. New test: assert `replicated ≤ durable` after every commit, pull, and restart.
4. **Compile-enforced stage discipline (T4).** "Stage 2 doesn't re-parse" was a rule a builder could break without noticing; make it impossible instead. Stage 1 returns an unexported **`verifiedEntry`** type holding its parsed struct and its exact buffer slice; stage 2 and the append path accept **only** that type. Then no code path can hand stage 2 an entry stage 1 didn't produce, and the compiler enforces it.
5. **Stub honors the contract (T5).** The Phase 1 stub release target stores its deduplication keys **durably**, keyed by entry hash, and answers the "was this key released?" query from that store. In-memory keys would let the crash tests pass for the wrong reason — a stub that forgets keys on restart would silently re-send and the test would prove nothing.
6. **Follower re-join rule (T6, recorded).** Re-join a follower **only while another follower is current**, or run at least two followers. Rationale: if the single follower wipes and re-joins, already-released entries exist only on the sequencer until it catches up; recomputing replicated height from current claims (T1) stops *new* releases but cannot protect past ones.
7. **Claude's closings recorded for the Proof Log.** S2 (short writes fatal — **confirmed as the right call**), S3 (outbox concurrency), S5 (bridge revisit list), S6 (consistency fixes) are **closed as specified**. S1's **contract half** (release-target contract) is closed; its **gating half** closes with T1+T2. With T1–T3 applied, Claude has **no further findings** on the Phase 1 packet at the spec level — his declaration, with the scope stated above.

## Revision 10 — 2026-10-19 (post sixth review): what changed and why

Claude's sixth review (received 2026-10-19 ~10:31 CDT via Damien Hall) found the open area is the **release outbox**: where the "released" marks live, and how they interact with the sequencer-restore rule. Headline finding **S1** — the marks are sequencer-local, so a restore-from-follower wipes them and the startup drain would re-send all history; and the Q7 double-release known limit has a cheap fix. Damien Hall approved Luna's recommended decision: **the outbox releases only entries at least one follower has pulled** — nothing irreversible happens on one machine's word alone; a release isn't real until the network has witnessed the entry. Applied below.

1. **Release only replicated entries (S1).** The outbox fires a release **only** for entries at or below the **replicated height** — at least one follower has pulled the entry (the sequencer observes this from follower pull requests). A released entry then survives a restore-from-highest-follower **by construction**, which **closes** Q7's double-release known limit (the Revision 9 recorded limit is retired — it is no longer a limit). Cost, stated explicitly: payout latency equals the follower pull interval; with zero followers up, releases stay pending — and that is **loud** on `/status`. **Release-target contract (specified now, binds the future bridge):** Phase 1's release target is a stub, but the contract is written now so the bridge cannot plug in an API that breaks it — the target must support **permanent deduplication by entry hash** (idempotency key = entry hash) and a **"was this key released?" query**, so marks can always be rebuilt from the target and never depend on sequencer-local state. Why it matters: restore-from-follower wipes sequencer-local marks, so without the contract the startup drain would re-send every redeem in history and exactly-once would rest on the target's key-retention policy (typically 24h–days, not forever).
2. **Short writes are fatal (S2).** A short write is **fatal**, like an fsync error (ruling 7): halt; the startup truncation cleans the tail. Partial bytes on disk followed by a 4xx and continued running would land the next append after garbage — mid-file corruption that refuses startup. B2's per-entry fsync makes short writes more likely (many writes per batch), so the rule is explicit. The scratch overlay is **never merged** after any write or fsync error. New test: inject a short write during adoption → commit → restart → assert a clean boot.
3. **Outbox concurrency (S3).** **One** outbox worker. An in-process set of in-flight keys. The startup scan covers only heights **≤ startup height**; live commits enqueue only heights **above** it. **Followers never run the outbox** (role check) — only the sequencer releases. New test: startup drain concurrent with 100 redeem commits against a fake target that counts sends per key → exactly one send per key.
4. **Stage discipline (S4).** Stage 2 consumes **the exact structs stage 1 produced** from the **exact immutable buffer** (P8a), and those same bytes are what get appended — the stages can never disagree on what an entry is (stage 2 does not re-parse or re-read). The stateful link checks are **named as stage 2**: the first suffix entry's `prev_hash` against the **live tip hash** (the tip cannot be read safely outside the lock), and recomputed-vs-stored R/C/floor. Overlay writes become live state **only after that entry's fsync succeeds** (B2 per-entry commits); nothing in the overlay is merged on any error path. New state-hash tests: after a **rejected** batch, a hash of live state is byte-identical to before; after an **accepted** batch, live state equals a fresh full replay. (The Q3 reflection test checks aliasing; these check merge correctness.)
**Revision 11 additions.** **Replicated height (T1):** the sequencer's config lists its followers; only pulls from those addresses count toward replicated height. A follower's request `from = h` is its **claim** that it durably holds everything up to h−1 — a claim about its own durable height, not about a response it received; any `from` greater than durable height + 1 is ignored. Replicated height = max over configured followers of (from − 1), **recomputed from current claims**, never a high-water mark. Followers must run on separate hardware from the sequencer. **Startup drain gated (T2):** one gate for every release path — `height ≤ replicated height`, including the S3 startup scan; after any restart replicated height starts at 0 and rebuilds from follower pulls. **Heights (T3):** durable height = the fsync frontier = the acknowledged frontier (alias only); replicated height is tracked only by the sequencer; ordering invariant **replicated ≤ durable**; live state matches durable because live state is only updated after fsync. `/sync` serves up to **durable**; `/status` reports **durable** and (on the sequencer) **replicated**; the outbox releases at or below **replicated**; commits and 200 responses happen at **durable**.
5. **Bridge revisit list (S5, recorded — not Phase 1).** When the bridge phase maps keys to real destinations, it must: (1) resolve the mapping **as of the commit height** and record which version was used — a mapping change between signing and release must not redirect funds; (2) require **more than the key** to change a mapping — identity re-verification plus a delay (key compromise is total: today the key both authorizes and receives); (3) introduce destination binding as a **new op schema version** (`grove-v2` redeem), never by editing v1 — v1 signatures stay valid; (4) **drain and close the Phase 1 outbox before the bridge starts** — Phase 1 releases still pending at cutover would otherwise pay into the new mapping.
6. **Consistency fixes (S6).** (a) Revision 8 item 3(b) is reworded: snapshots are guaranteed by the **two-stage overlay rule** (Q3, ruling 48), not "P2's deep-copy rule" — the deep-copy wording is superseded and retained only as history; a top-down reader meets no contradiction. (b) The Q2 fill-rate math uses the **hex journal line size** (~2× canonical binary bytes + 1 for the newline), not the canonical size — otherwise the days-to-fill estimate is about half what it should be. (c) The Q2 known-limit text now names **budget exhaustion** too: an attacker burning the global intake budget starves honest writes with 429/503 before the disk fills — the same outage class, reached faster.

## Revision 9 — 2026-10-19 (post fifth review): what changed and why

Claude's fifth review (received 2026-10-19 ~10:20 CDT via Damien Hall) found three findings that matter: **Q1** — the signed redeem payload carries no destination, so the release has nowhere to pay; **Q2** — the P1 watermark turned a fatal halt into a network-wide 503, but free deposits still buy a write outage, and the budget covered only the push path while followers and snapshots were ungated; **Q3** — the P2 deep copy is a hand-written field list in Go whose cost grows with the attacker's free accounts. Damien Hall approved all of Luna's recommendations, and confirmed the Q1 reasoning himself: the redeem pays out to the account itself because the protocol's job ends at the key — the person crosses into the physical world themselves via the regulated bridge, where identity verification lives. Applied below.

1. **Redeem destination = the account itself (Q1).** The 1:1 redeem release pays out to the **redeeming account key, by definition**. No signed destination field in Phase 1 — there are no payout rails in the trial, so a destination field would be dead spec with nothing to validate against; the payload format stays as-is through the clean break. The bridge-phase destination mapping (key → verified real-world payout destination) is a later phase's work, where identity verification lives. Rationale, his words: the protocol ends at the key — it is on the person to align themselves with a steady-backed coin in order to make their money in the physical world, and they do that through the regulated bridge.
2. **Disk-fill as a recorded trial limit (Q2).** "Disk-fill gives a write outage" is a **known, bounded, LOUD** Phase 1 trial limit — not solved by making deposits cost something (a cost mechanism in valueless test tokens is theater; the attacker mints free keys either way). The packet documents the fill rate the budget allows (entries/sec → days-to-fill for a reference disk size) so the operator knows the box's endurance. Regardless, all four gaps are closed: (a) **one global intake budget across HTTP and push paths** (not push-only); (b) the **watermark applies to every append on every role** — a follower below it stops pulling, keeps serving reads, and reports itself as lagging; (c) **compaction snapshots gated**: keep only the latest snapshot, snapshot failure is never fatal (it is a cache), and watermark headroom is set above the maximum snapshot size; (d) the check is `free − appendSize ≥ watermark`, not `free ≥ watermark`.
3. **Two-stage `VerifyFrom`, no deep copy (Q3).** The Revision 6/7 deep-copy snapshot is **superseded**. `VerifyFrom` splits into: **(1) stateless checks** — parse, canonical bytes, domain, grammar, Ed25519 signatures — run **outside** the lock, touching no state; **(2) stateful checks** — nonce, balance, floor, aggregates (cheap integer ops) — run **under** the lock against live state through a **scratch overlay discarded on failure**. Startup runs both stages in the same order — still one function, no drift, no `Clone()` hand-list, and the cost under the lock is bounded by K, never by the account count. New reflection test: walk `State` and assert no map/slice/pointer in the scratch overlay aliases the original, under `-race`.
4. **Idempotent release outbox (Q4).** The committed redeem entry **is** the durable intent. An **outbox worker** sends each release with **idempotency key = entry hash**, **outside** the serialization lock (a slow external system must never stall commits). At startup the outbox drains every committed redeem not yet marked released — finishing pending effects, not replay re-executing them (replay never fires releases). Mark released **only on confirmation**; retry with backoff when the release target is down; report pending releases on `/status`. This closes both crash windows: crash after fsync but before release → the outbox drains it at startup; release-before-fsync is impossible — the entry is enqueued only after fsync success. New test: crash between fsync and release → restart → exactly one release with that key (no double-fire, none lost).
5. **Admission controls stay out of `VerifyFrom` (Q5).** Watermark, role, rate budget, and disk state are **outside** the shared verify path — a node sitting at its watermark that restarts must boot and serve reads, never brick. New test: disk at watermark → restart → boots, serves reads.
6. **Hex journal lines (Q6).** The journal line is the **hex encoding of the canonical binary serialization that is already hashed** — one representation; `encoding/json` is never involved; malleability is impossible by construction; no Go-toolchain-upgrade brick risk. **Supersedes** the P8(c) re-encode rule (re-encoding JSON lines would fail after a toolchain change to escaping/output bytes).
7. **Sequencer restore rule (Q7).** **Restore the sequencer only by pulling from the highest follower — never from an older backup.** Followers hold only durable sequencer bytes (P3), byte for byte. An older backup rolls the sequencer back: followers are then ahead and not a prefix (they wedge), and already-fired releases reappear as balances (double release). Known limit recorded: releases from entries the sequencer made durable but no follower had pulled before the sequencer's disk died stay unrecoverable.
8. **Small items (Q8).** Property-test edges: `genesisState` is the empty state **before** entry 0, and `VerifyFrom` checks entry 0 at empty height; include `h = 0` (the joiner case); for invalid chains use only split points where `chain[:h]` is valid. **Fsync the journal once at startup** before declaring the durable height — after a `kill -9`, un-fsync'd page-cache bytes are still on disk and must not be treated as committed. The P6 wedge is **loud**: `state: wedged` on `/status` plus a `/metrics` counter — clients must never read a silently stale node.

## Revision 7 — 2026-10-19 (post fourth review): what changed and why

Claude's fourth review (received 2026-10-19 ~10:14 CDT via Damien Hall) found the headline hole **P1**: free self-signed deposits pushed to the sequencer fill its disk — rate limits cap speed, not total — until the next append fails, the fsync-fatal rule fires, and all writes network-wide stop. It also found the suffix-only tradeoff's weak point (**P2**: the snapshot as a hand-written field list lets the adoption check and the boot check drift apart), a follower-wedging path (**P3**: `/sync` serving entries before they are durable), and seven refinements. Damien Hall approved both of Luna's decisions — **P6** logged as a known Phase 1 limit (no TLS pinning now) and **P4** payout fires exactly once at sequencer commit — plus all mechanical fixes, with the standing instruction that decisions run through his cycles, loops, and patterns. Applied below.

1. **Disk-fill watermark (P1).** A free-space watermark is checked **before** every journal append. Below the watermark the sequencer returns **503** on writes and adoptions but stays up for reads — disk-full is predictable and must never reach the fsync-fatal path (ruling 7). A **global entries-per-second budget** applies to the push path: rate limits cap total intake, not just instantaneous rate. New test: fill the disk to the watermark → writes get 503, reads work, no halt.
2. **One verify function (P2).** `VerifyFrom(state, entries)`: startup calls `VerifyFrom(genesisState, fullChain)`; adoption calls `VerifyFrom(snapshot, suffix)`. The snapshot is a **deep copy of the same state type `apply` uses** — never a hand-maintained field list — so the two call sites cannot drift apart. `VerifyLedger` remains the named full-chain entry point. New property test: for random valid and invalid chains and random split points h, `VerifyFrom(snapshot(h), chain[h:])` must equal `VerifyLedger(chain)` every time.
3. **Durable-height serving (P3).** `/sync` serves entries only up to the **durable height** — the last height whose fsync succeeded — the same rule `/status` follows. Bytes that haven't fsync'd are never served: after an fsync failure the sequencer halts (ruling 7) and may commit a different entry at that height on restart, which would wedge any follower that pulled the pre-failure bytes. New test: inject fsync error after a write → pull concurrently → restart the sequencer → the follower still syncs.
4. **Payout exactly once at sequencer commit (P4).** The 1:1 redeem release fires **exactly once per committed redeem entry**, on the **sequencer**, in the commit path shared by HTTP writes and adopted pushes. It **never** fires during follower adoption or startup replay — those rebuild history; they do not re-execute effects. A pushed redeem that passes full suffix verification **is** a sequencer-committed op: push vs HTTP is not the distinction; commit vs replay is. New static check: grep the payout/release call site — confirm it is not inside `apply()` or the replay loop.
5. **Follower genesis refusal (P5).** Only `role: sequencer` may create a genesis. A follower started without a genesis file **refuses to start with an explicit error** — it never silently founds its own network. New test: start a follower without a genesis file → explicit startup error.
6. **Network-position attacks: known Phase 1 limit (P6).** Spoofed DNS / ARP answers on a follower's pull path are a **known Phase 1 limitation**, closed properly by Phase 2 sequencer signatures (followers will tell sequencer-made entries apart). No TLS pinning in Phase 1. Recorded in §4 known limits.
7. **Split serve/adopt limits (P7).** Separate limits for the `/sync` serve (GET) path and the adopt (POST) path; serving is bounded too — bulk range reads cost bandwidth and disk IO, so a push flood must not starve follower catch-up.
8. **Byte-exact append (P8).** (a) No buffer reuse across records — append exactly the single bounded body buffer, or copy each record (`bufio.Scanner.Bytes()` slices are overwritten by the next `Scan()`). (b) Every received record must end in `\n` with nothing trailing, else reject. (c) The strict parser re-encodes each record and requires the bytes to match exactly — the hash covers the binary canonical serialization, not the journal line, so non-canonical line encodings must not sit verbatim in the journal.
9. **Range mechanics (P9).** An adoption range starts at **local height + 1**; its first entry's `prev_hash` must equal the **local tip hash** (equivalent to the byte-prefix check — the hash covers every field). Overlapping ranges must be **byte-identical** or the range is rejected. `K` = **1,000** entries per range (builder may tune with written justification). The tip is confirmed by **hash, not height**. Short writes are errors.
10. **Small items (P10).** Timestamps **never drive logic** (recorded alongside "never checked"). **No promotion in Phase 1**: if the sequencer dies, no follower is promoted — acknowledged-but-unpulled entries would be lost and the old sequencer would return as a fork; the documented follower re-join procedure is wipe the journal, keep the genesis file, re-sync ranges. `/status` reports the node's **role and height**. §5 A1(b) label corrected: single-sequencer is enforced by the **role config** (Revision 6), not the prefix rule.

## Revision 6 — 2026-10-19 (post third review): what changed and why

Claude's third review (received 2026-10-19 ~10:07 CDT via Damien Hall) found the headline hole **N1**: prefix-extension protects the history a node *has*, but an attacker can push a short valid self-signed extension onto a follower and partition it from the sequencer permanently — the single-sequencer condition was still assumed, never enforced. It also found a remotely triggerable crash (N2: verifying outside the lock races live Go maps — fatal, unrecoverable), a contradiction between two Revision 5 fixes (N3: M5's full-loader temp-journal undoes M1's suffix bound), and seven medium/low refinements. Damien Hall approved all of Luna's recommendations, with the standing instruction that decisions run through his cycles, loops, and patterns. Applied below.

1. **Sequencer role in config (N1).** Exactly one node is `role: sequencer`; followers return 4xx on all writes and pull `/sync` **only** from the configured sequencer address — they never adopt pushed chains. The sequencer keeps inbound `/sync` live for the trial's attackers (a pushed valid extension there is just bulk-submitting signed ops). "Gate, not disable" now applies to the sequencer's inbound path; followers are pull-only. The single-sequencer condition moves from assumption to mechanism.
2. **Batched-append adoption (N3).** The received suffix bytes are parsed with the loader's record parser (bytes verified == bytes written, keeping M5's invariant) → verified against an immutable snapshot → **appended to the existing journal + fsync, under the lock**. No journal rewrite, no rename, no temp copy. This supersedes Revision 5's temp-journal+rename design and moots H2 (stale fd — the fd never changes). A crash mid-append leaves a valid shorter extension + torn tail, handled by the existing torn-tail rules. Rewrite-and-rename is only needed for real fork resolution = Phase 2.
3. **Immutable snapshot under lock (N2).** Before verifying outside the lock: under the serialization lock, take an immutable snapshot of `(R, C, floor, B, N, tip hash, height)`. Verify the suffix against the snapshot outside the lock; re-take the lock, confirm the tip still matches the snapshot height, then append. (Verifying against live maps is a Go fatal map race — an unrecoverable crash, i.e. a remote kill as specified.)
4. **Bounded ranges (N4).** `/sync` serves **and** accepts bounded ranges — from height `h`, at most `K` entries per request/response. A truncated extension is valid under the prefix rule, so joiners catch up in steps. Caps are per-attempt (suffix length and bytes per attempt), never total chain height.
5. **Join procedure (N5).** Genesis file present + journal empty = **"awaiting entry 0"**: writes refused; the first adopted range must begin with an entry 0 whose hash equals the genesis file. Join procedure documented: copy the genesis file → start the node → sync ranges. A node given a genesis file never silently founds its own network.
6. **Streaming caps (N6).** The request-body byte cap is enforced **while reading** via `http.MaxBytesReader` — a 10 GB buffered body is a remote OOM kill before any cap is checked. A **global concurrent-adoption limit** plus **rate-limit by /64 IPv6 prefix** (per-IP alone is defeated by 2^64 addresses per /64). The rotating sync-attempt log caps **total** bytes including rotated files (count × size).
7. **Commit timestamps (N7).** Commit stamps `max(wall-clock now, prev entry timestamp)` — informational only, never checked by `VerifyLedger`. A dead-CMOS box committing after a clock reset must not self-brick.
8. **Fixed-width integers (N8).** `uint64`/`int64` for amounts, sums, and indices everywhere in `apply()`, serialization, and index arithmetic — on 386, Go `int` is 32-bit and overflows past 2^31 where amd64 would not. Static check recorded: `vault/` at `35bb1d3` contains **no float usage** — the "pro-rata unchanged vs integer-only" contradiction does not exist; pro-rata keeps its existing integer remainder behavior. The cross-arch replay test must include amounts above 2^32.
9. **Re-issue refinements (N9).** The expiry window is measured in **ledger height, not wall time** (a wall-clock expiry reintroduces the year-2000 problem). Proof-of-orphaning **bounds** sequencer-misbehavior risk rather than removing it — a dishonest sequencer could resurrect superseded ops; prefer the owner's fresh signature where possible. Recorded: an owner who signed two different ops at the same nonce on two forks gets both executed — correct only where both had real external effects; redeem stays bounded by balance, so it can't inflate.
10. **Suffix boundary + truncate at startup (N10).** Suffix-only verification checks the **first suffix entry with full context**: `prev_hash` vs local tip, floor ≥ local floor, nonce == `N(a)+1`, aggregates continuing from local values. Torn tails are truncated **at startup**, not just before the next append — otherwise the byte-prefix comparison is undefined against garbage.

## Revision 5 — 2026-10-19 (post second re-verification): what changed and why

Claude's second re-verification (received 2026-10-19 ~10:00 CDT via Damien Hall) closed R1/R2/R4/R7 for the check itself but found the headline hole **H1**: deposit authorization proves *who signed*, not that anything backs it — an attacker can generate their own keys and build a longer, fully-valid chain from our public genesis at zero cost, and longest-chain would discard every honest user's history. The single-sequencer condition was assumed, never enforced. Damien Hall approved all of Luna's recommendations ("I trust you, let's run it"). Applied below.

1. **Prefix-extension adoption (closes H1).** `/sync` adopts a candidate chain **only if the local chain is a byte-identical prefix of it**. Only the suffix is verified — starting from local state, with the full `VerifyLedger` on the suffix. Under the serialization lock, the local tip is re-checked (it hasn't moved) before the swap. True forks (divergent history) are **rejected and logged** until Phase 2 fork rules exist — deferred, not denied. Consequences: the sync-discard attack flips to PASS (acknowledged ops can never be discarded — the candidate must contain them); the #1 acceptance claim becomes "only prefix-extending chains with fully valid suffixes are adopted"; longest-chain still decides between two valid extensions. Rationale: the Phase 1 trial is single-sequencer — there are no legitimate forks in Phase 1 — and the rule is mechanical and identical on every node: no human decides which history is "more valid." 2. **H2 — stale fd.** Under the lock, after adoption renames the journal into place, the commit path **reopens its journal file descriptor before the lock is released** — otherwise the next commit appends into the unlinked old inode, returns 200, and the op is gone forever. New test: adopt → commit one op → restart → assert the op is present.
3. **H3 — log bounding.** The Revision 4 "per-peer sync-attempt logging" is refined: a **capped, rotating log (or separate volume) PLUS a per-source rate limit on `/sync`**. Logging alone is not throttling — unbounded attacker-driven writes would fill the disk, fail the next fsync, and halt the node (ruling 7) through a side door. New test: flood `/sync` until the log hits its cap → assert the journal still commits.
4. **M1 — starvation bound.** The candidate **suffix** is verified **outside** the commit lock; then the lock is taken, the tip re-checked, and the swap performed. Under the prefix rule only the suffix is verified, so cost is bounded by new entries, not chain length. New test: adoption attempts with the bad entry placed last → commit latency stays under a bound.
5. **M2 — corrected assertion.** The R3 concurrency test now asserts: **every 200'd op is in the post-adoption chain**, with `/status` agreeing. The old "or re-rejected" wording blessed discard and contradicted the sync-discard criterion.
6. **M3 — re-issue constraints (recorded now, mechanism Phase 2).** (a) Re-issue requires the owner's **fresh signature OR a proof of orphaning** — evidence the op was committed on the losing fork (Phase 2 peer/sequencer signatures supply this). "No owner liveness" alone would let anyone execute any signed-but-never-committed op later (a delayed replay of an op the owner superseded). (b) A re-issue **expiry window** is recorded; its exact length is Phase 2's call. (c) Re-issue does **not** consume the sequential nonce — exactly-once is keyed by **(account, original nonce, payload hash)**, so no third party can grief the owner's next nonce.
7. **M4 — per-attempt caps (refines Revision 4).** Cap **work per adoption attempt** (suffix length and bytes per attempt), **not total chain height** — the journal is never pruned and there are no checkpoints, so a total-height cap would one day stop fresh nodes from syncing entirely. The prefix rule gives this naturally: the suffix *is* the attempt's work.
8. **M5 — bytes, not structs.** The candidate is written to a **temp journal**; the **exact startup loader** runs on that temp file; the rename happens only if it passes. The invariant must hold on bytes, not on parsed structs — a lossy wire→struct→disk round trip would verify one thing and boot another. New fuzz test: any candidate adoption accepts must produce a temp file the boot loader accepts byte-for-byte.
9. **M6 — clock-free.** `VerifyLedger` is **clock-free**: no check compares timestamps against "now." Rationale: ruling 3 welcomes old hardware, and old hardware with a dead CMOS battery boots in the year 2000 — a chain adopted today must boot after a clock reset.
10. **M7 — integer-only.** `apply()` uses **integer-only arithmetic** — no floats anywhere in the transition function. (Go may fuse `x*y+z` into FMA on arm64/ppc64/s390x; a recomputed aggregate differing by one ulp across architectures would boot on one box and brick on another.) Crash-matrix item 6 gains a cross-arch deterministic-replay test (amd64, arm64, 386).
11. **Binary-upgrade note (Low, not a build item).** A future stricter `VerifyLedger` could refuse a chain an older binary adopted. Versioning of `VerifyLedger` must be addressed **before any change to it ships** — recorded here so it isn't discovered later.

## 1. Goal

Give every ledger entry an identity — account, nonce, and signature — so the node can prove *who* owns *what*, reject replays even across restarts and syncs, and commit each operation as one durable atomic transition. Concretely: per-account balances derived only from replaying authenticated entries; nonces stored inside entries (the separate nonce file is deleted); the fsync'd journal append is the single commit point; a read-only `/status` endpoint lets clients resolve ambiguous timeouts. **Scope is deposit, redeem, and tip only.** Claim transfer, outside-gift-as-an-operation, and internal-reserve-movement are cut from Phase 1 by Damien Hall's 2026-10-18 ruling (transfer is parked as the first Phase 2 operation; gift and movement revisit when Basin 5 exists). ## 2. Binding requirements, as buildable checks

- **OWN-01 — Verified claim ownership.** `B(a)` (account a's redeemable balance) is derived *only* from replaying authenticated ledger entries. Never from a stored snapshot, never from the last entry's cached totals. `Verify()` **recomputes** `R`, `C`, and `floor` from replay and **requires equality** with the values stored on each entry; the `C` in `Σ_a B(a) == C` is the recomputed one. Stored-vs-recomputed divergence is a verification failure, not a warning — allowing it would strand non-replayable entries on disk and force a second clean break later. After every committed transition the node asserts `Σ_a B(a) == C`; a mismatch rejects the transition before commit. `redeem` with `amount > B(a)` → reject (4xx), no entry appended, no nonce consumed. Floor units are never counted in `B(a)` or `C`. **Tip jar:** tips credit `R` and `floor` only; the jar is not an account inside `ΣB(a)==C`, and nothing can redeem from it — tips ratchet the floor upward and are non-redeemable by design.
- **AUTH-01 — Replay-rejecting authorization.** Every mutation carries: Ed25519 pubkey (= account), op type, canonical **operation-specific** payload, domain separation, nonce, signature. Verify *before* any state change. Reject: bad signature, wrong domain, stale nonce (`nonce != N(a)+1` — nonces are **strictly sequential**, the locked de-facto rule), reused nonce. **Account encoding is strict:** at every parse boundary the account must be exactly 64 lowercase hex characters; uppercase, `0x` prefixes, wrong lengths, and whitespace are rejected with 4xx. Never silently normalize — mixed canonicalization (e.g., signature check lowercasing while the nonce table keys on the raw string) re-opens the B3 case-split. Balances and nonce tables are keyed by decoded pubkey bytes. **Amount grammar:** positive integer only (`amount > 0`); canonical decimal (no leading zeros, no `+`, no whitespace, no fractional forms — `"+5"`, `"05"`, `"5.0"` are distinct byte-strings and all rejected); an explicit `MAX_AMOUNT` below 2^62 with overflow-checked sums. **Fixed-width integers (N8):** amounts, sums, and indices are `uint64`/`int64` everywhere — on 386, Go `int` is 32-bit and overflows past 2^31 where amd64 would not. Static check recorded: `vault/` at `35bb1d3` contains no float usage — the integer-only rule matches existing code; pro-rata keeps its existing integer remainder behavior. **Duplicate `(account, nonce)` is rejected inside the transition function** `apply(entry)` — the same function `Verify()` and startup replay call — so a hand-built chain with a duplicated deposit entry is refused at startup, not just at the HTTP layer. A consumed nonce stays consumed across restart and across sync adoption. The ledger preserves account + nonce + signature per entry so any third party can replay-verify deterministically.
- **ATOM-01 — One durable atomic transition.** All effects of one accepted op — changes to `(R, C, F, B, N, K, P, H)` — commit via a single fsync'd journal append. **Commit ordering (exact):** validate → authorization check → serialize the candidate entry → append to journal → `f.Sync()` → **if fsync errors: halt the process (fatal, no retry)** without mutating live in-memory state and without responding 200 (a failed fsync cannot be safely retried — the kernel may drop dirty pages and report the next fsync clean) → on fsync success: swap the candidate into live state → respond 200. Live in-memory state is never mutated before the fsync returns success. Crash recovery yields the complete transition or none; partial application is impossible by construction. The separate `nonces.json` is deleted; `N(a)` is rebuilt from the ledger at startup. **Record framing:** one record per line, newline-delimited, with the PR #10 boundary contract (torn *final* record tolerated; corruption anywhere else refuses startup). A torn tail is **truncated at startup** (N10) — otherwise the byte-prefix comparison in adoption is undefined against garbage; truncating only before the next append leaves windows where no candidate's bytes can ever match. **Locking:** validate-through-fsync runs under a single serialization lock, so two copies of one signed op cannot both pass the nonce check. **Documented limits:** file fsync is performed; directory fsync is not — the code assumes VFS-atomic rename for compaction files, and power loss during compaction is outside the tested crash model (pre-spec §13.5). This must be stated in the builder doc, not implied.
- **AUTH-02 — Keys grant no privileges.** A valid signature authenticates the signer; it authorizes nothing by itself. No privileged operations exist in Phase 1 beyond the three user ops, so this is enforced structurally: there is no code path where "signed" implies "permitted." **Sync adoption gate (Phase 1, Revision 5):** the governing invariant is **ADOPTABLE ⊆ BOOTABLE**, enforced by **prefix-extension adoption** — `/sync` adopts a candidate chain **only if the local chain is a byte-identical prefix of it**. Only the suffix is verified, starting from local state, with the full **`VerifyLedger`** (v1 parse with the strict parser, per-entry domain == configured genesis, signature validity, strictly-sequential nonces with no duplicates, amount grammar, `floor[i] >= floor[i-1]`, recomputed R/C/floor == stored, entry 0 is `kind: genesis` with hash == configured genesis). `VerifyFrom` runs in two stages (Q3): **stateless checks** (parse, canonical bytes, domain, grammar, signatures) **outside** the commit lock, touching no state; then the lock is taken and **stateful checks** (nonce, balance, floor, aggregates) run against live state through a scratch overlay **discarded on failure**. (N2's warning stands — verifying against live maps is a Go fatal map race, i.e. an unrecoverable remote kill — but the Revision 6/7 deep-copy snapshot is withdrawn: Go has no built-in deep copy, so a hand-written `Clone()` is a field list again, and copying `B` on every attempt lets an attacker grow the cost for free.) Then the lock is taken, the stateful checks run against live state (the range's first `prev_hash` must still match the live tip hash — a moved tip fails the range), and the suffix is **appended to the existing journal + fsync** (N3: batched append — no rewrite, no rename, no temp copy; H2's stale-fd problem is moot because the fd never changes). A crash mid-append leaves a valid shorter extension plus a torn tail, handled by the torn-tail rules; rewrite-and-rename is only needed for real fork resolution = Phase 2. **Why prefix, not full-chain re-verify:** Claude's H1 showed that authorization proves *who signed*, not backing — anyone can manufacture a longer, fully-valid, self-signed chain from the public genesis at zero cost, and plain longest-chain would discard every honest user's history. The Revision 3 full-chain gate closed forged history but not *validly-signed divergent* history. Prefix-extension closes it: the candidate must *contain* our history, so acknowledged ops can never be discarded. True forks (divergent history) are **rejected and logged** until Phase 2 fork rules exist — deferred, not denied. Longest-chain still decides between two valid extensions. **Bytes, not structs (M5, via N3):** the received suffix bytes are parsed with the **loader's record parser**, so the bytes verified are exactly the bytes appended — the invariant holds on the bytes that will boot, not on re-serialized structs. No temp journal, no rename. **Clock-free (M6):** `VerifyLedger` makes no comparison against "now" — old hardware with a dead CMOS battery boots in the year 2000 and must still boot the chain. **Disk write:** adoption **appends** the verified suffix to the existing journal + fsync, under the lock (N3). There is no rename and no second file — the fd never changes, so H2 (stale fd after rename) cannot occur. A crash mid-append leaves the old chain plus a valid shorter extension and a torn tail — never a mixture — handled by the torn-tail rules, which truncate at startup (N10). **Batched-adoption commit semantics (B2):** each suffix entry is **independently committed** — appended and fsync'd one at a time, in order; the acknowledged adoption frontier is the **last durable entry**. A crash mid-batch leaves a valid shorter extension + torn tail as the *defined outcome*, not a violation. Whole-batch atomicity is explicitly **rejected** for Phase 1 (no two-phase commit). The commit boundary is exact: **only entries at or below the durable height are treated as committed; anything above is torn tail** — a failed fsync never leaves unacknowledged records that a restart mistakes for committed operations (ChatGPT engineering note (c)). **Bounded ranges (N4):** `/sync` serves **and** accepts bounded ranges — from height `h`, at most `K` entries per request/response. A truncated extension is valid under the prefix rule, so joiners catch up in steps. Caps are per-attempt (suffix length and bytes per attempt), never total chain height (the journal is never pruned; a total-height cap would one day stop fresh nodes syncing). **Entry-0 rule (no special-casing):** entry 0 must be `kind: genesis` with `hash(entry 0) == configured genesis`; entries 1+ carry `domain == genesis`. **Sequencer role (N1, Revision 6):** exactly one node is configured `role: sequencer`; all others are followers. **Followers return 4xx on all writes** (deposit/redeem/tip) and **pull `/sync` only from the configured sequencer address** — they never adopt pushed chains. The sequencer keeps inbound `/sync` live for the trial's attackers (a pushed valid extension there is just bulk-submitting signed ops). Rationale: the Phase 1 trial is single-writer; there are no legitimate follower pushes to lose. The single-sequencer condition moves from assumption to mechanism — no operator discipline required, no silent follower partitions (Claude N1: a pushed valid extension would otherwise cut a follower off from the sequencer for the rest of Phase 1). "Gate, not disable" now applies to the sequencer's inbound path; followers are pull-only. **Re-derivation:** the suffix already passed `VerifyLedger`, so `apply` during `B(a)`/`N(a)` re-derivation cannot fail — stated, not assumed. Damien Hall's binding direction stands: gate, not disable — `/sync` stays live for the trial's attackers. The two stale-table behaviors remain specified as bugs: (a) adopted-chain signatures re-appliable locally because the old table survived; (b) dropped local ops stuck "used" while `/status` says unknown. Full peer-registration/sync-adoption authorization (Ed25519 peer signatures, bounded retries) stays Phase 2 per the Sync Hardening packet.
**Revision 7 additions.** **Disk-fill watermark (P1):** a free-space watermark is checked **before** every journal append. Below the watermark the sequencer returns **503** on writes and adoptions but stays up for reads — disk-full is predictable and must never reach the fsync-fatal path (ruling 7). A **global entries-per-second budget** applies to the push path: rate limits cap total intake, not just instantaneous rate. **Durable-height serving (P3):** `/sync` serves entries only up to the **durable height** (the last height whose fsync succeeded) — the same rule `/status` follows. Bytes that haven't fsync'd are never served. **Payout exactly once (P4):** the 1:1 redeem release fires **exactly once per committed redeem entry**, on the **sequencer**, in the commit path shared by HTTP writes and adopted pushes. It **never** fires during follower adoption or startup replay — those rebuild history; they do not re-execute effects. A pushed redeem that passes full suffix verification **is** a sequencer-committed op: push vs HTTP is not the distinction; commit vs replay is. **Split limits (P7):** the `/sync` serve (GET) path and adopt (POST) path have **separate** limits, and serving is bounded too — bulk range reads cost bandwidth and disk IO, so a push flood must not starve follower catch-up. **Byte-exact append (P8):** (a) no buffer reuse across records — append exactly the single bounded body buffer, or copy each record; (b) every received record must end in `\n` with nothing trailing, else reject; (c) the strict parser re-encodes each record and requires the bytes to match exactly. **Range mechanics (P9):** an adoption range starts at **local height + 1**; its first entry's `prev_hash` must equal the **local tip hash** (equivalent to the byte-prefix check — the hash covers every field). Overlapping ranges must be **byte-identical** or the range is rejected. `K` = **1,000** entries per range (builder may tune with written justification). The tip is confirmed by **hash, not height**. Short writes are errors.
**Revision 8 additions.** **Phase 1 authorization authority (B1):** a reserve-increasing entry is **authorized if and only if the sequencer includes it** — the sequencer is the designated Phase 1 authorization authority. Phase 1 moves valueless test assets only, so external settlement evidence is vacuous in Phase 1; the production settlement-evidence rule (converter settlement proofs, peer signatures) is Phase 2. This is an explicit, mechanically checkable rule, not a deferral: authorization = sequencer inclusion, recorded in the ledger itself. A follower has no commit path and therefore cannot authorize history.
**Revision 9 additions.** **Redeem destination = the account itself (Q1):** the 1:1 redeem release pays out to the redeeming account key, by definition — the protocol's job ends at the key; the person crosses into the physical world through the regulated bridge, where identity verification lives. No signed destination field in Phase 1; the bridge-phase key→destination mapping is later work. **Outbox (Q4):** the committed redeem entry is the durable intent; an outbox worker executes each release with idempotency key = entry hash, outside the serialization lock; startup drains committed-but-unreleased redeems (finishing pending effects, never replay re-executing); mark released only on confirmation; retry with backoff; report pending on `/status`. **Two-stage verify (Q3):** `VerifyFrom` runs **stateless checks** (parse, canonical bytes, domain, grammar, signatures) outside the lock, then **stateful checks** (nonce, balance, floor, aggregates) under the lock against live state through a scratch overlay discarded on failure — superseding the Revision 6/7 deep-copy snapshot. **Admission controls (Q5)** — watermark, role, rate budget, disk state — stay outside the shared verify path: a node at its watermark that restarts must boot and serve reads, never brick. **Journal lines are hex** of the canonical binary serialization (Q6), superseding the P8(c) re-encode rule. **Sequencer restore (Q7, closed by S1):** restore only by pulling from the highest follower, never from an older backup — followers hold only durable sequencer bytes (P3), byte for byte. The Revision 9 known limit (releases from unpulled entries dying with the sequencer's disk) is **closed**: the outbox fires only at or below the replicated height (S1), so every released entry is on at least one follower by construction.
**Revision 10 additions.** **Release gating (S1):** the outbox fires a release **only** for entries at or below the replicated height — at least one follower has pulled (observed from follower pull requests). Nothing irreversible happens on one machine's word alone: a release isn't real until the network has witnessed the entry. With zero followers up, releases stay pending, loud on `/status`. **Release-target contract:** the target (a stub in Phase 1) must support **permanent deduplication by entry hash** and a **"was this key released?" query** — marks are rebuilt from the target, never trusted to sequencer-local state (restore-from-follower wipes local marks; without this the startup drain re-sends all history). **Short writes are fatal (S2):** halt like an fsync error (ruling 7); the overlay is **never merged** after any write or fsync error. **Outbox concurrency (S3):** one worker, an in-process set of in-flight keys, startup scan covers only heights ≤ startup height, live commits enqueue only heights above it, followers never run the outbox (role check). **Stage discipline (S4):** stage 2 consumes the exact structs stage 1 produced from the exact immutable buffer (P8a), and those same bytes are what get appended; the first suffix entry's `prev_hash` against the **live tip hash** and recomputed-vs-stored R/C/floor are named as stage 2; overlay writes become live state only after that entry's fsync succeeds, never on any error path.
- **STATUS-01 — Read-only status.** `GET /status?account=<hex>[&nonce=<n>]` returns `{balance: B(a), last_nonce: N(a), ledger_height, tip_hash}`, and with `&nonce=` whether that specific nonce is consumed. Read-only, informational, never authorizes a mutation. Responses are derived from **durable state only** — never from pre-fsync in-memory state — and keyed by **(account, nonce), never by signature** (signature lookup admits malleability front-running). "If the status source is stale, unavailable, or inconsistent, the client must not interpret that as proof an operation failed." **Retry semantics:** retrying the *same* (account, nonce, signature) is always safe — a repeated committed nonce never causes a second transition (at-most-once application; the client may receive a rejection rather than a replayed success, which is fine). What the client must not do is mint a *new* nonce for an op whose fate is unknown.

## 3. Per-module work items

### identity/ — operation-specific payloads + genesis binding + strict key handling
1. Canonical **operation-specific** payload schemas (retires the fixed universal payload):
   - deposit: `grove-v1|<genesis-hash>|deposit|<account>|<amount>|<nonce>`
   - redeem: `grove-v1|<genesis-hash>|redeem|<account>|<amount>|<nonce>`
   - tip: `grove-v1|<genesis-hash>|tip|<account>|<amount>|<nonce>`
   - transfer (FUTURE, disabled in Phase 1): `grove-v1|<genesis-hash>|transfer|<sender>|<recipient>|<amount>|<nonce>`
   `<genesis-hash>` is the lowercase hex hash of ledger entry 0. The parser requires field[1] to be exactly 64 lowercase hex chars — a v0.3 five-field payload can never be byte-identical to a v1 six-field payload, and its op string in the hash position fails parse. There is exactly one verify function and no old-format fallback (add a grep test: no v0.3 payload builder outside test fixtures).
2. `Sign` and `Verify` take the genesis hash as a parameter; verification fails if the payload's domain field does not equal the node's configured genesis.
3. **Strict account handling (replaces the old normalize bullet):** reject non-canonical encodings at every parse boundary (uppercase, `0x`, wrong length, whitespace) with 4xx; key balances and nonce tables by decoded pubkey bytes. Add tests: upper-vs-lower hex for the same key → the upper is rejected, nothing consumed; re-submission of a committed op with uppercased account → 4xx.
4. Reserve the `grove-v1-peer|` payload tag now for Phase 2 peer signatures, so a peer signature can never verify as an op payload even if key types overlap.

### ledger/ — entry schema carrying identity, two verify functions
5. New `Entry` struct:
   `{index, timestamp, prev_hash, hash, domain, account, nonce, signature, kind, amount, R, C, floor, network_id}`
   - `domain`: entry 0 carries `""`; entries ≥1 carry the genesis hash (breaks the self-reference: genesis is `hash(entry 0)` with entry 0's domain empty by convention).
   - `network_id`: entry 0 carries 16 random bytes (hex); bound into the entry-0 hash so every genesis is unique. **No default genesis ships in the repo** — otherwise every trial instance shares a domain and ops replay across instances.
   - `account`: lowercase hex pubkey, empty for `genesis` entries.
   - `nonce`: the consumed nonce for user ops; 0 for `genesis`.
   - `signature`: the hex signature authorizing this entry; empty for `genesis`.
   - `kind`: `genesis | deposit | redeem | tip`. The transition function rejects `genesis` at any index ≠ 0.
   - `R, C, floor`: resulting aggregates after this entry's transition. Stored for readers; **authoritative values come from recomputation** (§2 OWN-01).
6. **Canonical serialization, fixed now:** field order as in the struct; integers as fixed-width 8-byte big-endian; byte strings length-prefixed (4-byte big-endian length + bytes). No JSON-object hashing anywhere in the hash input — Go map iteration must not affect it. `computeHash` covers **every** field explicitly, including `signature`, `domain`, `account`, and `nonce` (Phase 2 peer signatures hash entries; anything unbound now breaks them later) — **except the entry's own `hash` field**. `computeHash(entry)` **MUST** hash the canonical serialization of all committed entry fields **excluding** the entry's own `hash` field: the `hash` field is the resulting digest, stored afterward. Verification **MUST** recompute the digest using the same exclusion rule and compare it with the stored hash. Hashing the entry's own `hash` field is a circular definition (`H = SHA256(Encode(..., H, ...))`) that no builder can implement deterministically. Ship a test vector with a fixed expected hash **computed with this exclusion rule** — the test vector MUST cover this exact procedure. **Journal line encoding (Q6):** the journal line is the **hex encoding of the canonical binary serialization** — one representation; `encoding/json` is never involved; malleability is impossible by construction; no Go-toolchain-upgrade brick risk. This **supersedes** the P8(c) re-encode rule (re-encoding JSON lines could fail after a toolchain change to escaping/output bytes). New test: hex-line round trip — decode, parse, re-encode → bytes identical.
7. Two verify functions, named exactly:
   - `VerifyChainHash(chain)`: hash linkage only (`prev_hash`/`hash` chain intact). Retained as a named primitive; it is **no longer sufficient as an adoption check** (Revision 3: the adoption path must call `VerifyLedger`).
   - `VerifyLedger(chain)`: everything — v1 parse with the strict parser, per-entry domain == configured genesis, signature validity, nonce strictly sequential per account with no duplicates, amount grammar, `floor[i] >= floor[i-1]`, recomputed R/C/floor == stored, entry 0 is `kind: genesis` with hash == configured genesis. **Clock-free (M6):** no check compares timestamps against "now" — old hardware with a dead CMOS battery boots in the year 2000 and must still boot the chain. **One function, two stages (P2, Q3):** both call sites go through **`VerifyFrom(state, entries)`** — startup calls `VerifyFrom(genesisState, fullChain)`; adoption calls `VerifyFrom(localState, suffix)`. Stage 1 (stateless: parse, canonical bytes, domain, grammar, signatures) runs outside the lock; stage 2 (stateful: nonce, balance, floor, aggregates) runs under the lock against live state through a scratch overlay discarded on failure — no deep copy, no `Clone()` hand-list (Q3 supersedes the Revision 6/7 deep-copy snapshot). (S4: stage 2 consumes stage 1's exact structs from the same immutable buffer — the same bytes appended; the first-suffix-entry `prev_hash` vs **live** tip hash and recomputed-vs-stored R/C/floor are stage-2 checks; overlay merges only after per-entry fsync success, never on any error path.) `VerifyLedger` remains the named full-chain entry point. Used by startup **and** by the adoption path on the candidate suffix before swap (ADOPTABLE ⊆ BOOTABLE, enforced via prefix-extension in Revision 5). Both refuse on any failure.
8. On fresh start the node writes entry 0 (`kind: genesis`, all quantities zero, random `network_id`) and records its hash in the genesis **file** (ruling 2). Startup rules: genesis file missing + journal empty → create (**sequencer only** — P5: a follower in this state **refuses to start with an explicit error**; only `role: sequencer` may create a genesis, so a follower never silently founds its own network); genesis file missing + journal non-empty → **refuse to start with an explicit error** (never derive the genesis from journal data — whoever can write the journal would choose the domain); genesis file **present** + journal empty → **"awaiting entry 0"** (N5): writes refused; the first adopted range must begin with an entry 0 whose hash equals the genesis file — a node given a genesis file never silently founds its own network; genesis file present + entry-0 hash mismatch → refuse to start. **Join procedure (documented):** copy the genesis file → start the node → sync bounded ranges.
9. Journal mechanics per PR #10 hold, plus the §2 ATOM-01 additions: torn tail truncated at startup (N10); single serialization lock on the commit path; fsync error is fatal. **Compaction:** the journal is **kept** (no pruning — pruning would make balances unrecoverable from replay and violate OWN-01 by construction). Phase 1 startup **never reads the snapshot**; it is a write-only performance cache. The every-1000 snapshot write is **post-commit maintenance**, outside the atomic transition: the op's append+fsync+response completes first; a crash during compaction must not un-commit the op (PR #10 recovery governs). Test: write a snapshot with altered balances → restart → `B(a)` equals pure replay; delete the snapshot → restart → identical results. **Snapshot gating (Q2):** keep only the **latest** snapshot; a snapshot write failure is **never fatal** (it is a cache); watermark headroom is set **above the maximum snapshot size** so a snapshot write can never push the disk past the watermark (compaction is post-commit maintenance — it must never reach the fsync-fatal path).

### vault/ — per-account accounting, replayable state machine
10. Add `B map[string]uint64` (decoded-pubkey-keyed) to the vault state. Transition rules:
    - `deposit`: `R += amount; C += amount; B[a] += amount`.
    - `redeem`: require `B[a] >= amount` else reject; `B[a] -= amount; C -= amount; R -= amount` (existing impairment/pro-rata payout policy unchanged).
    - `tip`: `R += amount; floor += amount`; `B` and `C` untouched (tip economics unchanged).
11. After every committed transition, assert `Σ_a B(a) == C` (INV-01, recomputed C). On violation: refuse to commit, count `InvariantViolations`, log.
12. The vault transition function is *pure and replayable*: `apply(entry) -> state | error`, no wall-clock, no randomness, no map iteration affecting output — and it enforces the duplicate-`(account, nonce)` check and the amount grammar itself, so `Verify()` and startup replay share one enforcement point. This is what startup rebuild and (in Phase 2) staged sync replay call. **Integer-only (M7):** `apply()` uses integer-only arithmetic — no floats anywhere in the transition function. (Go may fuse `x*y+z` into FMA on arm64/ppc64/s390x; a recomputed aggregate differing by one ulp across architectures would boot on one box and brick on another.) **Fixed-width (N8):** `uint64`/`int64` for amounts, sums, and indices — never bare `int`. Static check: no float usage in `vault/` at `35bb1d3`. Cross-arch deterministic replay is crash-matrix item 6.

### node/ — single atomic commit, nonce cache, status endpoint, adoption gate
13. **Delete the nonce file.** Remove `nonces.json`, `loadNonces`, `saveNonces`, `commitNonce`. At startup, rebuild `N(a)` by replaying the ledger through the vault state machine. The nonce table is a cache; the ledger is the truth.
14. **Commit path (exact order):** validate → authorization check → serialize candidate entry → journal append → `f.Sync()` → on fsync error: **halt** (no retry, no state mutation, no 200) → on success: swap into live state → **enqueue the release in the outbox** (redeem entries only — the committed entry is the durable intent, §2 Q4; the outbox fires only for entries at or below the replicated height, S1) → respond 200. All under the single serialization lock. The entry's `timestamp` is `max(wall-clock now, prev entry timestamp)` (N7) — informational only, never checked by `VerifyLedger`; a dead-CMOS box committing after a clock reset must not self-brick. **Timestamps never drive logic** (P10) — recorded alongside "never checked". **Admission controls (Q5)** — watermark, role, rate budget, disk state — are enforced on the HTTP/adopt intake paths, **never inside `VerifyFrom`**: a node sitting at its watermark that restarts must boot and serve reads, never brick.
15. **Failed ops (any 4xx) consume nothing:** no nonce consumed, no entry appended, no state mutated (ruling 1, locked).
16. `GET /status?account=<hex>[&nonce=<n>]` per §2 STATUS-01: durable-state only, keyed by (account, nonce). The response also carries the node's **role** (`sequencer`/`follower`) and **height** (P10) — so a client reading a stale follower knows it.
17. **Adoption path (Revision 6):** **prefix-extension** — adopt only if the local chain is a byte-identical prefix of the candidate; verify only the suffix from local state with full `VerifyLedger`. **Sequencer role (N1):** only nodes configured `role: sequencer` adopt pushed chains; followers return 4xx on writes and pull `/sync` only from the configured sequencer address. **Two-stage verify (N2, Q3 supersedes the Revision 6/7 deep-copy snapshot):** `VerifyFrom` runs **stateless checks** — parse, canonical bytes, domain, grammar, Ed25519 signatures — **outside** the lock, touching no state; then the lock is taken and **stateful checks** — nonce, balance, floor, aggregates (cheap integer ops) — run against live state through a scratch overlay **discarded on failure**. Startup runs both stages in the same order — one function, no drift, no deep copy; the cost under the lock is bounded by K, never by the account count. (The Revision 6/7 deep-copy snapshot is withdrawn: Go has no built-in deep copy, so a hand-written `Clone()` is a field list again — and copying `B` on every attempt lets an attacker grow the cost for free via fresh keys. No copy, no drift, no attacker-scalable cost.) **Stage discipline (S4):** stage 2 consumes **the exact structs stage 1 produced** from the **exact immutable buffer** (P8a), and those same bytes are what get appended — stage 2 never re-parses or re-reads, so the stages cannot disagree on what an entry is. The stateful link checks are named as stage 2: the first suffix entry's `prev_hash` against the **live tip hash** (the tip cannot be read safely outside the lock), and recomputed-vs-stored R/C/floor. Overlay writes become live state **only after that entry's fsync succeeds** (B2 per-entry commits); **nothing in the overlay is merged on any error path**. **Batched append (N3):** parse the received suffix bytes with the loader's record parser (bytes verified == bytes written, keeping M5's invariant), then append to the existing journal + fsync under the lock — no rewrite, no rename, no temp copy (H2 moot: the fd never changes). A crash mid-append leaves a valid shorter extension + torn tail, handled by the torn-tail rules. (P8: no buffer reuse across records — append exactly the single bounded body buffer, or copy each record; every received record must end in `\n` with nothing trailing, else reject; journal lines are hex of the canonical binary serialization — **Q6 supersedes** the old re-encode-and-compare rule.) **Short writes are fatal (S2):** halt like an fsync error; the overlay is never merged after any write or fsync error. **Bounded ranges (N4):** serve and accept at most `K` entries from height `h` per request/response; joiners catch up in steps. (P9: ranges start at **local height + 1**, and the first entry's `prev_hash` must equal the **local tip hash** — equivalent to the byte-prefix check since the hash covers every field; overlapping ranges must be **byte-identical** or the range is rejected; `K` = **1,000** entries unless the builder justifies otherwise in writing; the tip is confirmed by **hash, not height**; short writes are **fatal** (S2).) **Streaming caps (N6):** enforce the request-body byte cap **while reading** via `http.MaxBytesReader` (a 10 GB buffered body is a remote OOM kill); a **global concurrent-adoption limit** plus **rate-limit by /64 IPv6 prefix** (per-IP alone is defeated by 2^64 addresses per /64); the rotating sync-attempt log caps **total** bytes including rotated files (count × size). (P7: the serve (GET) and adopt (POST) paths have **separate** limits; serving is bounded too — a push flood must not starve follower catch-up.) **Disk-fill watermark (P1, Q2 gaps closed):** a free-space watermark is checked **before** every journal append — the check is `free − appendSize ≥ watermark` (an adoption appends up to K entries, so `free ≥ watermark` alone is wrong); below it the node returns **503** on writes and adoptions but stays up for reads — disk-full must never reach the fsync-fatal path. A **single global entries-per-second budget** applies across the **HTTP and push paths** (a push-only budget is bypassed through HTTP). The watermark applies to **every append on every role**: a follower below it stops pulling, keeps serving reads, and reports itself as lagging. (Known limit recorded in §4: disk-fill gives a write outage — bounded, loud, and measured, not solved.) **Durable-height serving (P3):** `/sync` serves entries only up to the **durable height** (the last height whose fsync succeeded) — bytes that haven't fsync'd are never served. **Payout exactly once (P4):** the 1:1 redeem release fires **exactly once per committed redeem entry**, on the **sequencer**, in the commit path — never during follower adoption or startup replay. **Destination = the account itself (Q1):** the release pays out to the redeeming account key, by definition — the protocol's job ends at the key; the person crosses into the physical world through the regulated bridge, where identity verification lives. No signed destination field in Phase 1. **Outbox (Q4, S1, S3):** the committed redeem entry is the durable intent; an outbox worker executes each release with **idempotency key = entry hash**, **outside** the serialization lock (a slow external system must never stall commits). **Replicated-height gating (S1):** the outbox fires **only** for entries at or below the **replicated height** — at least one follower has pulled the entry (observed from configured followers' pull requests — T1: only pulls from addresses in the sequencer's configured follower list count; a follower's `from = h` is its claim of durable hold through h−1; `from > durable height + 1` is ignored; replicated height = max over configured followers of (from − 1), recomputed from current claims, never a high-water mark; followers must run on separate hardware). **Replication claims bound to the fsync frontier (R11):** a follower MUST construct every `from` **exclusively** from its verified, fsync-confirmed durable frontier — receipt, parsing, successful verification, buffered writes, and pending adoption do **not** advance it; after restart the follower MUST recover and verify its durable frontier before issuing any replication claim; the sequencer MUST NOT count a follower claim beyond its own durable frontier. This **closes** the Revision 9 Q7 known limit: every released entry survives restore-from-highest-follower by construction. Cost: payout latency equals the follower pull interval; with zero followers up, releases stay pending — loud on `/status`. **Release-target contract:** the target (a stub in Phase 1) must support **permanent deduplication by entry hash** and a **"was this key released?" query** — release marks are rebuilt from the target, never trusted to sequencer-local state (restore-from-follower wipes local marks). **Concurrency (S3):** exactly **one** outbox worker; an in-process set of in-flight keys; the startup scan covers only heights ≤ startup height while live commits enqueue only heights above it; **followers never run the outbox** (role check). At startup the outbox drains committed-but-unreleased redeems — finishing pending effects, never replay re-executing them; mark released **only on confirmation**; retry with backoff when the target is down; report pending releases on `/status`. (Static check: the release call site must not be inside `apply()` or the replay loop.) **Suffix boundary (N10):** the first suffix entry is checked with full context — `prev_hash` vs local tip, floor ≥ local floor, nonce == `N(a)+1`, aggregates continuing from local values. **Sequencer restore (Q7, closed by S1):** restore the sequencer **only by pulling from the highest follower — never from an older backup**; an older backup rolls the chain back (followers wedge; already-fired releases reappear as balances = double release). The Revision 9 known limit — releases from entries the sequencer made durable but no follower had pulled — is **closed**: the outbox fires only at or below the replicated height, so every released entry is on at least one follower by construction. **Loud wedge (Q8):** a pull that detects a fork sets `state: wedged` on `/status` plus a `/metrics` counter — clients must never read a silently stale node. Atomic `B(a)`/`N(a)` re-derivation on swap. True forks rejected and logged. Everything else about `/sync` is unchanged in Phase 1. **Revision 11 additions (T1–T6).** The S3 startup drain is explicitly gated by `height ≤ replicated height` — one gate for every release path; replicated height resets to 0 on every restart and rebuilds from follower pulls, so releases pause until a follower checks in. **Stage discipline is compiler-enforced (T4):** stage 1 returns an unexported **`verifiedEntry`** type (parsed struct + exact buffer slice); stage 2 and the append path accept only that type — no code path can hand stage 2 an entry stage 1 didn't produce. The Phase 1 stub release target stores its deduplication keys **durably**, keyed by entry hash, and answers "was this key released?" from that store (T5). Follower re-join: only while another follower is current, or run at least two followers (T6, recorded). **Rationale for the record:** (unchanged from Revision 5) authorization proves who signed, not backing — prefix-extension closes Claude's H1 without staged replay (no merge, no peer signatures, no retries): the candidate must *contain* our history, so acknowledged ops can never be discarded. Only validly-signed *extensions* remain; divergent history is Phase 2's fork-resolution job.

## 4. Non-goals (do not build)

- No `transfer` operation (parked for Phase 2; its schema is defined in §3.1 but the op is disabled — the transition matrix has no transfer row yet).
- No checkpoints, no pruning, no Merkle `state_hash` snapshots (pre-spec §12 deferred). `compactEvery = 1000` snapshot behavior stays as-is, write-only, never read at startup.
- No peer-registration or sync-adoption *authorization* changes beyond B1 (Ed25519 peer signatures = Phase 2, Sync Hardening packet). The Phase 1 authorization rule is explicit: **authorization = sequencer inclusion** (ruling 44). The `VerifyLedger` adoption gate **is** Phase 1 — it is validation, not authorization.
- No tip economics changes; no issuance ratios, floor equations, or redemption payout policy inventions (contract §4 defers these to the pre-spec).
- No minimum-cement / entry-term mechanics (not Phase 1).
- **Trial topology (N1):** one node holds `role: sequencer`; all other trial nodes are followers — 4xx on writes, pull-only `/sync` from the sequencer address. Multi-writer operation is Phase 2.
- **Known Phase 1 limitation (P6):** network-position attacks on follower pulls (spoofed DNS, ARP on a home LAN or shared Wi-Fi) are **not** defended in Phase 1 — no TLS pinning. This is closed properly by Phase 2 sequencer signatures, when followers can tell sequencer-made entries apart. Recorded here so it is a known limit, not a discovered hole.
- **No promotion in Phase 1 (P10):** if the sequencer dies, no follower is promoted — acknowledged-but-unpulled entries would be lost, and the old sequencer would return as a fork. Documented follower re-join procedure: wipe the journal, keep the genesis file, re-sync ranges. (Downtime = network-wide write outage; acceptable for the trial if stated.)
- **Known Phase 1 trial limit (Q2):** disk-fill gives a write outage. Free self-signed deposits mean an attacker can fill the disk to the watermark, after which the network returns 503 on writes until an operator adds disk. This is bounded and loud by design (watermark on every role, one global intake budget across HTTP and push, reads stay up, follower-lag and wedge signals on `/status`/`/metrics`) — **not** solved by a deposit cost mechanism, which in valueless test tokens would be theater (the attacker mints free keys either way). The builder doc **must state the fill rate** the budget allows (entries/sec → days-to-fill for a stated reference disk size), so the operator knows the box's endurance and the trial measures the real attack rate. The fill-rate math must use the **hex journal line size** (~2× the canonical binary bytes + 1 for the newline), not the canonical size — otherwise the days-to-fill estimate is about half what it should be. The limit text also names **budget exhaustion**: an attacker burning the global intake budget starves honest writes with 429/503 before the disk fills — the same outage class, reached faster.
- **Bridge revisit list (S5, recorded — not Phase 1):** when the bridge phase maps keys to real payout destinations, it must: (1) resolve the mapping **as of the commit height** and record which version was used — a mapping change between signing and release must not redirect funds; (2) require **more than the key** to change a mapping — identity re-verification plus a delay (key compromise is total: today the key both authorizes and receives); (3) introduce destination binding as a **new op schema version** (`grove-v2` redeem), never by editing v1 — v1 signatures stay valid; (4) **cutover rule:** drain and close the Phase 1 outbox before the bridge starts — Phase 1 releases still pending at cutover would otherwise pay into the new mapping.
- **Recorded for later (not a build item):** a future stricter `VerifyLedger` could refuse a chain an older binary adopted. Versioning of `VerifyLedger` must be addressed **before any change to it ships** — this note exists so the problem is found here, not in production.

47. **Disk-fill as a recorded trial limit (Q2).** "Disk-fill gives a write outage" is a known, bounded, loud Phase 1 trial limit — not a problem to solve with a deposit cost mechanism, which in valueless test tokens would be theater (the attacker mints free keys either way). Rationale: the trial is a recon probe — the limit is bounded (watermark on every role, one global budget across HTTP and push), loud (503, metrics, reads stay up, lag/wedge signals), and measured (fill rate documented), so the operator knows the box's endurance and the trial measures the real attack rate.
48. **Two-stage `VerifyFrom`, no deep copy (Q3).** Stateless checks outside the lock; stateful checks under the lock against live state through a scratch overlay discarded on failure. Supersedes the Revision 6/7 deep-copy snapshot. Rationale: Go has no built-in deep copy — a hand-written `Clone()` is a field list again, and copying `B` on every attempt lets the attacker grow the cost for free. No copy, no drift, no attacker-scalable cost.
49. **Idempotent release outbox (Q4).** The committed redeem entry is the durable intent; an outbox worker executes each release with idempotency key = entry hash, outside the serialization lock; startup drains committed-but-unreleased redeems; mark released only on confirmation; retry with backoff; report pending on `/status`. Rationale: exactly-once across both crash windows — crash after fsync but before release is recovered by the startup drain; release-before-fsync is impossible because the entry is enqueued only after fsync success.
50. **Admission controls stay out of `VerifyFrom` (Q5).** Watermark, role, rate budget, and disk state are enforced on the intake paths, never inside the shared verify path. Rationale: a node at its watermark that restarts must boot and serve reads — admission logic in the boot path turns a full disk into a brick.
51. **Hex journal lines (Q6).** The journal line is the hex encoding of the canonical binary serialization. Supersedes the P8(c) re-encode rule. Rationale: one representation, no JSON involved, malleability impossible by construction, no Go-toolchain-upgrade brick risk.
52. **Sequencer restore rule (Q7).** Restore the sequencer only by pulling from the highest follower — never from an older backup. Rationale: followers hold only durable sequencer bytes (P3), so the highest follower is the freshest safe source; an older backup rolls the chain back and resurrects already-fired releases as spendable balances (double release).
53. **Small items (Q8).** Property-test edges defined (`genesisState` = empty state before entry 0; include h = 0; invalid chains split only where the prefix is valid); fsync the journal once at startup before declaring the durable height; the P6 wedge is loud (`state: wedged` + `/metrics` counter). Rationale: served means durable; a silently stale node is a lying node.

## Rulings — 2026-10-19, tenth round (Damien Hall, on Luna's recommendation — standing instruction: decisions run through his cycles, loops, and patterns; no new decisions required — every item is a mechanical application of standing rules, recorded explicitly)
60. **Replicated height from configured followers only (T1).** The sequencer's config lists its followers; only their pull claims count toward replicated height. `from = h` = durable hold through h−1; `from > durable height + 1` is ignored. Replicated height is tracked only by the sequencer. ## Addendum — 2026-10-19 (Damien Hall)
**CPU-DoS bounding on the adoption path.** Full VerifyLedger on unauthenticated /sync input is bounded mechanically: candidate chain size cap, verification aborts on the first failing entry, per-peer sync-attempt logging (peer identity recorded with every attempt). Rationale, his words: the meeting happens because you chose the peer — the trust decision comes first; precautions don't prevent robbery, they make it expensive and traceable. Public place, time limit, receipts. No human judgment in the moment.

**Reputation lives outside the protocol.** The protocol provides unforgeable attributable evidence (signed history, bound identity); third-party platforms may build trust-tracking communities (yay-or-nay on a coin or account). Reputation is advisory, never permissioning — no one is barred from dealing with anyone; the information is collective, the decision stays with the individual. The base layer MUST NOT score trust (that would be a central arbiter in costume). Recorded as a protocol non-goal; platform reputation systems own their own failure modes (Sybil, collusion, cold start).

**Build posture.** By the time machines roll out, updates are hardening ahead of flaws, not fixes for flaws found in the wild. The mechanism for that posture is this loop: contract → attack review → formalizer verdict → revision, before a line of code ships. Three revisions before build is the posture working.
